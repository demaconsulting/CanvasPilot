# OTS Dependencies

This document provides the integration and usage design for all Off-The-Shelf (OTS) software
items used by CanvasPilot. The per-item files under `docs/design/ots/` cover the
specifics of each individual OTS item. The OTS items are:

- **Runtime libraries** that are part of the delivered application: Avalonia (user interface framework),
  CommunityToolkit.Mvvm (view model source generators), CanvasNet (draws image source files), and Speech
  (audio devices and speech models).
- **Packaging tool**: WiX Toolset, which builds the Windows installer package.
- **Test framework**: xUnit, which runs the unit, user interface, and OTS tests.
- **Compliance, documentation, and analysis tools** that run in the build pipeline: BuildMark, FileAssert, Pandoc,
  ReqStream, ReviewMark, SarifMark, SonarMark, SysML2Tools, VersionMark, and WeasyPrint.

## Selection Criteria

OTS items are selected only when they satisfy the project's compliance and maintenance needs:

- The license shall be compatible with the project's MIT license and with redistribution of the
  built application.
- The item shall be actively maintained, with an established release history and a user community
  that reports and resolves defects.
- The item shall have an acceptable security track record, and vulnerabilities shall be
  addressed by the maintainers in a timely manner.
- Preference is given to items that provide qualification evidence of their own, such as a vendor
  self-validation suite that produces test results the build can consume, or that can be exercised
  through a small set of integration tests that call them the way the application does.

## Version Management Policy

OTS versions are pinned and upgraded deliberately. Dotnet tools are pinned in the tool manifest
(`.config/dotnet-tools.json`) and NuGet package references are pinned in the project files, so that
every build restores the same versions. Upgrades are initiated by Dependabot pull requests or by a
maintainer reviewing a new release. A major version change, or a change in the behavior of an
integration point described in the per-item design files, triggers a review of the affected design
and verification documents before the upgrade is accepted. Specific version numbers are not recorded
in design documentation; the tool versions used by each build are captured by VersionMark and
published in the build notes.

## General Integration Approach

Build, documentation, and quality tooling is consumed as dotnet tools restored from the tool
manifest and invoked as single, stateless process calls from the CI pipeline and from the local
`build.ps1`, `fix.ps1`, and `lint.ps1` scripts. The unit-testing framework (xUnit) is consumed
directly as a package reference by the test projects. Cross-cutting conventions are applied
consistently: a non-zero exit code from any OTS tool fails the build, and generated outputs are
written to `generated/` folders or the `artifacts/` folder and are never committed. Runtime libraries, such as
Avalonia, CommunityToolkit.Mvvm, CanvasNet, and Speech, are NuGet package references of the application; they are
called in process from the unit or units that use them, and the seams described in the subsystem designs keep the rest
of the application and its tests independent of them. The WiX Toolset is consumed as an MSBuild SDK by an installer
project that is built only by the Windows build job.

## Qualification Strategy

OTS items are qualified by the strongest evidence each one can supply, together with pipeline
output assertions. Tools that have a self-validation suite are run by the pipeline, and the
results are recorded as test evidence linked to the item's OTS requirements. For documents produced by OTS
tools, FileAssert assertions confirm that the expected outputs exist and have the expected content.
Runtime libraries without a self-validation mode (Avalonia, CommunityToolkit.Mvvm, CanvasNet, and Speech) are
qualified by tests in `test/OtsSoftwareTests` that call the library the way the application does, and the WiX Toolset
is qualified by a FileAssert assertion on the package it builds. Before a version upgrade is accepted, the vendor's
release notes are reviewed and the self-validation, OTS test, and FileAssert evidence is regenerated by the pipeline
and confirmed to pass.

## Scope

OTS items are third-party tools and libraries consumed by the project. This document covers the
integration pattern and usage design for each item. The internal design of OTS items is out of
scope; only how this project integrates and uses each item is documented.
